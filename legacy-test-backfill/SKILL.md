# 老项目测试补全 (Legacy Test Backfill)

通用、跨语言。不要假设任何具体技术栈、目录结构或工具——一切先自检、再按需替换。

## 何时用
- 给一个已有/遗留项目补测试、提升测试质量；
- 已有自动化测试但质量存疑，需要审查/重写/删减；
- 有缺陷库(Jira 等)和 git 历史，想把它们变成回归测试与风险地图。

## 你的目标
不是"加更多测试"，而是用**最少、最锋利**的用例覆盖**最可能伤到用户**的行为，
让人敢重构、敢发布。每个测试都是负债（要维护、拖慢 CI、可能脆性误报），
所以"删一个没价值的"和"加一个有价值的"同等重要。

## 贯穿全程的原则（宪法 · 每个流程都遵守）
═══════════════════════════════════════════════════════

**A. "好测试"的标准**：当且仅当"用户/调用方真正在乎的行为"坏了它才失败；
一红就能立刻定位坏在哪。一套好测试 = 给人重构/发布的信心，拦住真会伤用户的 bug，成本尽量低。

**B. 用例从"它该做什么"推，绝不从"它现在怎么写"抄。**
照着实现抄断言 = 把当前行为（连同 bug）锁死，且一重构就崩。这是头号陷阱。

**C. 用例来源按价值排序**：
1. 真实用户旅程 / 核心业务流程（最值钱）
2. 契约/规格的边界：等价类 + 边界值，找"行为翻转的那个点"（上限 N → 测 N 通过、N+1 拒绝），不是随便传 null
3. 高风险区：钱/交易、鉴权、权限、删除/级联、状态机、并发幂等
4. 历史 bug → 每个补一条回归测试

**D. 反模式（发现就标记，建议删/重写）**：测实现细节；软断言（只断言非空/没抛异常）；
flaky（依赖时序/顺序/外部状态）；噪音用例（传 null/空/list 这类好写没价值的，除非该输入真实会出现且处理错会伤用户）；
为覆盖率测 getter/setter 与样板代码。

**E. 每个用例的过滤尺**："如果删掉它，会有什么用户在乎的 bug 因此溜过去？"
答"没有" → 不写 / 删掉。

**F. 不拿数字当目标**：不给"X 行 = N 个测试"，不把行覆盖率当 KPI（古德哈特定律）。
质量用**变异测试**验收（见流程二·阶段5）。

## 关键认知：测试的"预言机问题"(test oracle)
═══════════════════════════════════════════════════════
遗留项目最大的难点：你手上只有代码，而**代码只能告诉你"它现在是什么"，不能告诉你"它该是什么"**。
要写有意义的测试必须知道期望值(oracle)，而它恰恰来自代码之外：
**需求、线上日志、历史 bug、前端编码进去的假设、领域常识、问人。**

因此两类测试要分清，别混：
- **特征测试(characterization)**：冻结"现在的行为"当安全网，**不判断对错**——危险区重构前先做。必须标注"冻结现状，待与意图对账"。
- **正确性测试**：基于意图(oracle)验证"该是什么"——需要外部材料才能写。

## 阶段 -1：栈与约定自检（任何流程开始前必做，零假设）
═══════════════════════════════════════════════════════
先探明、并向用户确认，**不要预设**：
1. 语言 / 框架；测试框架与**跑测命令**；测试目录与命名约定。
2. 覆盖率工具、**变异测试工具**（见下表，按栈替换）。
3. 跑测试的前置条件（需要 DB/容器/服务？mock 边界在哪？）。
4. 缺陷库在哪（**适配层**：Jira / GitHub Issues / GitLab / Linear / 仅 git commit）。
5. 需求/规格在哪（PRD / wiki / README / 无）。
6. 前端/客户端代码位置（用于推导用户旅程）。

| 语言 | 变异测试工具 | 语言 | 变异测试工具 |
|------|------------|------|------------|
| Java/Kotlin | PIT (pitest) | JS/TS | Stryker |
| Python | mutmut / cosmic-ray | Go | go-mutesting / ooze |
| C#/.NET | Stryker.NET | Ruby | mutant |
| Rust | cargo-mutants | PHP | Infection |

> 探不到就明说，并标注"该部分以降级置信度进行、假设需确认"。任何 oracle 来源缺失时按"降级策略"兜底（见末尾）。

# 流程一：历史 Bug 分析 → 回归用例 + 热点/根因图
═══════════════════════════════════════════════════════
目的不是"出一份 bug 报告归档"，而是产出两样**能直接用**的东西：
**【回归用例清单】** 和 **【热点/根因模式图】**。

### 步骤
1. **拉缺陷**（按缺陷库适配，需访问权限/导出）：优先筛 **线上的 / 高优的 / 客户报告的 / 已关闭**。
   - 无缺陷库时降级：扫 git 历史里 `fix:`/`hotfix`/`revert`/含 issue 号 的提交。
2. **关联修复提交**：用 ticket ID ↔ git commit/PR 对应。修复 diff 告诉你：**根因、改在哪个文件/函数、当时有没有补测试**。
3. **逐条抽四项**：
   - 触发场景 → 写成一条**回归用例**（注释关联 ticket/事故）
   - 根因类别（空值/边界/并发/状态机/鉴权/数据迁移/配置…）
   - 代码位置 → 计入**热点图**
   - 当时有无回归测试（没有 = 现在必须补）
4. **聚合分析**——这些 bug 体现的是系统性信号：
   - **热点聚集**：哪些模块反复出 bug → 又脆又复杂 → 测试火力往那压（bug 密度预测未来 bug）。
   - **根因模式**：反复出现的那一类 → **团队系统性缺哪一类测试**（如"API 层老漏空输入校验"→补一整类边界测试）。
   - **逃逸到线上的 bug = 当年测试套件没抓住的** → 每个都是"缺失用例"的铁证 → 全转回归。
   - **严重度/影响** → 用真实用户痛苦**校准风险地图**（把"我猜鉴权重要"变成"鉴权占了 N 次事故里的 M 次"）。
   - **修复有无配回归测试** → 没配的多 = bug 为什么反复，也说明流程要改。

### ⛔ 产出（停下给用户确认）
- 回归用例清单（每条：触发场景、关联 ticket、落在哪一层）
- 热点图（模块 × bug 数/严重度）
- 根因模式 Top N + 对应"该补哪一类测试"的建议

# 流程二：从材料 + 代码生成用例（带确认关卡，端到端）
═══════════════════════════════════════════════════════
⛔ 标记处必须停下，把产出给用户、等确认后再继续。不要一口气做到底。

### 阶段 0：收集上下文（oracle 来源）⛔
向用户索要；缺哪样就明说并降级：
1. **需求/PRD/业务规则**（"该是什么"的来源；可过时）
2. **线上日志/埋点/APM**（真实使用频率 → 排旅程优先级）
3. **历史 bug**（→ 走流程一；ROI 最高）
4. **前端/客户端代码**（用户旅程的可执行规格）
5. **跑测试方式 + 栈 + 现有测试约定**（来自阶段 -1）
6. **约束**：能否删测试？哪些目录别碰？时间/范围预算？只审查还是可动手？

⛔ 收齐或确认缺口后停下，汇报拿到了什么、缺什么，再进阶段 1。

### 阶段 1：分析项目（建立事实底座）
1. 读代码：API/路由面（= 能力清单）、数据模型与状态机、外部依赖边界。
2. **从前端推真实用户旅程**；用日志给旅程排重要性。
3. **盘点现有自动化测试**（当线索，不当规格）：
   - 抽它们断言的**业务行为**（不是机制）→ 一份"待确认的行为清单"；
   - 三方对账：行为清单 ↔ 需求 ↔ 代码 → 找隐藏规则、找缺口；
   - 按反模式给现有测试打分（留/重写/删）；
   - QA 的 E2E 常编码了真实旅程 → 拿来用，但 UI 录制类标"脆性高、需重写为语义选择器"。
4. **需求/文档 ↔ 代码逐条对账**，标 drift——不一致处要么文档过时、要么代码有 bug，两种都列出来。

产出《测试现状画像》：分层占比(UT/IT/E2E)、关键旅程清单、文档↔代码冲突点。

### 阶段 2：风险与缺口评估
1. **风险地图**：哪些行为坏了对用户伤害最大（结合流程一的根因/严重度校准）。
2. **反模式扫描**：按原则 D 列问题用例，指到具体文件/用例名。
3. **缺口分析**：高风险但没测到的行为（按"坏了多疼"排序）；空洞测试——伪变异自查"把这行改掉，会有测试变红吗？"不会红=摆设。

⛔ 把阶段 1+2 合成《审查报告》，请用户：(a) 纠正事实，(b) 补充代码/前端推不出的意图。确认后进阶段 3。

### 阶段 3：出用例方案 + 确认 ⛔
按优先级排序，分三栏：
- **【删除】** 低价值/噪音/flaky 用例 + 每条理由
- **【新增】** 用例，每条注明：来源(旅程/边界/风险/历史bug)、针对的行为、期望值从哪来(需求/日志/对账结论)、落在哪一层
- **【重写】** 测了实现细节、需改成测行为的用例

附：预估工作量、影响面、建议实施批次（高风险优先）。
⛔ 停下，等用户确认/调整方案，才进阶段 4。不要提前写代码。

### 阶段 4：实施（小批量、可回滚）
1. 按确认批次写，高价值优先；每批写完跑一次，确保绿、不引入 flaky。
2. 严守原则 A~E；断言验证真实结果，不许软断言。
3. "危险但完全没测"的遗留区：先写**特征测试**当安全网，标注"characterization：冻结现状，待与意图对账"，不假装在验证正确性。
4. 历史 bug 逐条补回归，注释关联 ticket/事故。
⛔ 删测试或大范围改动前，列出来让用户确认。

### 阶段 5：验收（客观衡量，不靠覆盖率自我感觉）
1. 跑全套，报告结果。
2. 对"钱/权限/核心逻辑"等关键模块跑**变异测试**（工具见阶段 -1 表），给杀死率与存活变异清单。杀死率低=注水，补那里，而不是加 null 用例。
3. 交付总结：新增/删除/重写了什么；风险覆盖前后对比；残留缺口与后续建议。

## 降级策略（oracle 来源缺失时的兜底）
═══════════════════════════════════════════════════════
| 缺失 | 兜底做法 |
|------|---------|
| 没缺陷库 | 挖 git 修复提交(`fix/hotfix/revert`/issue 号) |
| 没需求/文档 | 从代码+前端+旧测试**推断**行为清单，⛔ 必须让用户逐条确认对错 |
| 没前端 | 用 API 面 + 日志推导旅程 |
| 没日志 | 旅程优先级由用户/领域知识判断 |
| 不能跑变异 | 至少做"伪变异"静态自查(改一行会不会有测试红) |

## 全程语气
先报告、后动手；不确定就问；宁可少而准，不要多而虚。
skill 是通用的，**"什么算正确"永远由人按项目注入**——所以确认关卡(⛔)不能省。
