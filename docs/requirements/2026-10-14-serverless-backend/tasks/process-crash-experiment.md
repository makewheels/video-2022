# S12.b.1 进程终止与受理间隙实验

本批把S12.a的对象重建/合成异常扩展为真实子进程强制终止。实验程序只在测试目录，按既有`FcTaskSubmitter`的落库/认领/发送/响应顺序建立模型；**没有直接执行Java提交器，也没有生产任务实现或云队列验收**。

## 实验与判据

`serverless/tests/test_task_process_crashes.py`在独享回环Mongo随机库中启动独立解释器。子进程完成`w=1,j=true`写入后通知父进程，父进程强制终止它，再用另一客户端回读；没有依赖固定sleep、优雅退出或内存对象。辅助进程限制无认证回环连接和测试库前缀。

| 终止位置 | 持久状态 | 可以得出的结论 |
|---|---|---|
| 保存任务后、唤醒前 | CREATED及完整payload/deadline，通知为空 | 单纯先写Mongo再发消息存在无唤醒任务；删除扫描并不能消除该窗口 |
| 认领后、发送前 | SUBMITTED、无平台requestId、无模拟受理记录 | 认领成功不等于函数已经受理 |
| 模拟受理后、写响应前 | SUBMITTED、无requestId，模拟提供方有记录 | 与上一行的业务记录完全相同，不能据SUBMITTED或缺requestId立即重发收费任务 |
| 写响应后、确认消息前 | SUBMITTED及requestId | 业务状态可供重复投递核对；平台实际重投递仍须另验 |
| 完整意图通知先持久化、任务写入前 | 通知有完整快照，业务任务不存在 | 消费者若只查任务不存在就确认会丢工作；必须定义完整意图重建，而非裸taskId唤醒 |

另用16次并发重复认领验证：同一taskId/attemptId的CREATED仅一次CAS修改，payload、deadline和attempt计数不被覆盖。它证明Mongo原子认领，不证明外部副作用恰好一次。相同业务状态的未发送/已受理两种崩溃对照保留为明确的失败边界。

`syntheticWake`和`syntheticProvider`只是测试专属集合，分别表示持久通知与外部受理账本；既非真实队列也非FC实现，不作为新增生产集合/字段的决定。子进程终止不是Mongo崩溃、主机断电、真实FC停止或可见性超时实验。

## 对方案的约束

本机验收：Python3.12.13完整1091passed/0skipped/1既有Starlette弃用warning，含本批7项真实进程终止/并发测试，Ruff通过。独享Mongo进程、数据与依赖环境在系统临时目录，结束后清理；没有新增外部依赖、生产配置或真实云调用。

1. 不采用“Mongo保存成功→尽力发通知→关闭扫描”作为完整方案；无独立恢复依据会丢任务。
2. 不采用“通知先发一个taskId→找不到记录就确认”的消费者；需要可恢复的完整意图、稳定业务键和明确的响应丢失重投语义。
3. 保留既有attempt/截止时间和未知受理等待策略。重复通知不能增加业务attempt，平台重试计数不能直接映射业务重试。
4. 候选方向是托管持久意图受理与事件触发消费者，结合活跃任务的可靠deadline触发。业务受理确认、最大保留期、失败出口和Mongo写入/投递边界必须一起证明；只补一个队列适配器仍不满足S12。
5. 本批不启用任何生产入口，不删除Java恢复，不采购消息服务或新增RAM权限。S12.b仍有真实平台/延迟/保留期/死信实验未完成，S12.c–g不可标完成。

## 官方依据复核（2026-10-16）

- [FC异步任务](https://help.aliyun.com/zh/functioncompute/best-practices-for-asynchronous-tasks)描述异步受理和失败目标；这是平台生命周期，不能覆盖业务数据库跨系统原子性。
- [SMQ队列](https://help.aliyun.com/zh/mns/developer-reference/queue-queue)描述至少一次、可见性超时和消息有限保留，不能推导无限期不丢。只把最大值当候选能力，未指定为本项目配置。
- [SMQ与FC集成](https://help.aliyun.com/zh/mns/user-guide/function-compute-fc)支持队列/主题事件触发，可作为免自建常驻消费者的调查方向；空队列平台读取费用、北京可用性及延迟粒度仍待实际核对。

下一批先固定旧原片完成、MD5与任务受理所需完整意图和现有业务键，继续调查托管触发与deadline的失败恢复。涉及新业务字段/状态或同步受理语义变化时单列决策，不用本实验模型悄悄改变原协议。
